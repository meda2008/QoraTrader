# QoraTrader可转债交易策略平台宪法

## 核心原则

### I. 代码质量与可维护性原则
代码编写必须遵循高质量标准，确保清晰、简洁、可维护和可扩展。所有代码必须包含适当的注释和文档，特别是复杂算法和业务逻辑部分。代码需遵循项目定义的编码规范，通过静态代码分析工具验证质量。重构必须在测试覆盖下进行，确保代码质量持续改进。采用设计模式和最佳实践，避免代码重复，提高模块化程度。所有交易策略必须作为独立插件实现，遵循统一的策略接口规范，确保策略代码可独立开发、测试和部署，与核心交易引擎解耦。每个策略需提供完整的配置文件、参数优化空间定义和风险控制参数。所有代码都应能让新加入项目的开发者轻松理解。

### II. 全面测试与质量保障原则
**所有代码都必须严格遵循全面测试策略，包括单元测试、集成测试、端到端测试和性能测试。** 任何新功能或错误修复都严禁在没有相应测试覆盖的情况下进行开发。测试覆盖率必须达到95%以上，关键路径代码覆盖率需达到99%以上。开发工作流必须强制执行"测试-开发-重构"循环：1) 为每一个功能变更或修复，首先编写测试用例；2) 编写实现代码，确保测试通过；3) 在测试持续通过的保障下，优化代码结构。所有测试必须自动化，并集成到CI/CD管道中。任何策略在实盘部署前必须通过完整的历史数据回测验证，包括压力测试、极端市场条件测试和流动性测试。回测需包含完整的交易成本模型、滑点模拟和风险评估。策略参数优化需采用Walk Forward分析方法，避免过拟合。

### III. 工具一致性与API优先设计原则
项目将使用一套标准化的工具进行开发、构建、测试和部署。这确保了一致性，减少了配置偏差，并为所有团队成员简化了开发环境的搭建。任何新工具都必须经过批准并在项目的文档中记录。所有服务和组件都应采用 API 优先的方法进行设计。在开始实施之前，定义并记录 API 契约。这确保了组件的接口定义良好，并能满足其消费者的需求，特别是在策略接口、行情接口、交易接口等关键组件中。

### IV. 语义化版本控制与策略管理原则
项目严格遵守语义化版本控制 2.0.0。所有发布版本都必须采用 `主版本号.次版本号.修订号` 的格式。对于策略插件，同样采用语义化版本控制，主版本号对应重大策略调整，次版本号对应策略逻辑优化，修订号对应bug修复。策略配置文件必须明确指定策略版本，确保回测和实盘运行的一致性。

### V. 用户体验一致性与性能优化原则
**系统必须以卓越的用户体验和高性能为设计核心。** 所有面向用户的组件必须遵守通用的设计体系和交互模式，确保跨应用的界面元素、术语和工作流程保持一致，为用户提供可预测且直观的体验。系统性能要求包括：行情接收延迟<5ms，策略信号生成<50ms，订单执行<20ms，Tick到订单的平均延迟低于50ms。系统必须支持微秒级行情接收和订单执行能力。所有API端点必须满足已定义的性能基准，关键用户交互响应时间必须在100ms以内。系统需进行定期的性能基准测试，确保在高负载条件下仍能满足性能要求。前端界面必须流畅，无明显卡顿，响应时间应低于16ms以保持60fps的流畅体验。

## 安全与运维标准

### 配置与认证安全
敏感信息（如交易账户密码、API密钥）必须通过环境变量或专用密钥管理工具注入，严禁硬编码或明文存储。所有API端点必须通过JWT等机制进行认证和授权。数据库连接必须使用加密协议。

### 系统监控与可靠性
系统需提供完整的结构化日志记录功能，便于故障排查和性能分析。需实现断线重连与状态恢复机制，确保网络异常后能自动恢复。系统需具备容器化部署能力，支持Docker和Docker Compose进行一键部署。系统需具备实时性能监控和告警机制，确保交易时段核心服务可用性>99.9%。

## 代码质量标准

项目必须遵循严格的代码质量标准，包括但不限于：
- 版本控制：Git，遵循Git Flow工作流
- 持续集成：通过CI/CD管道自动执行测试和部署
- 代码格式化：采用统一的格式化工具（如black、isort用于Python，Prettier用于TypeScript）
- 静态分析：通过linter工具进行代码质量检查，确保无严重警告
- 复杂度控制：函数复杂度不超过10，类方法数量合理
- 命名规范：使用有意义的变量和函数名称，遵循项目命名约定
- 文档标准：所有公共API必须有完整的文档字符串

## 用户体验标准

所有面向用户的界面和API必须遵循统一的设计原则：
- API端点命名和数据结构保持一致性
- 错误消息格式标准化，提供明确的错误码和描述
- 配置参数命名和结构统一，提供清晰的默认值
- 日志格式标准化，便于系统监控和调试
- 用户界面遵循一致的视觉设计语言和交互模式

## 开发工作流与质量门禁

所有工作都应在从 `main` 分支创建的特性分支上进行。禁止直接向 `main` 分支提交代码。每个特性、错误修复或变更都必须创建一个拉取请求 (PR)。每个 PR 在合并前必须由至少一名其他开发者审查和批准。

在 PR 可以合并之前，必须通过以下质量门禁：
- 所有现有和新增的单元、集成测试都必须通过。
- 代码覆盖率必须达到90%以上。
- 代码必须遵守项目的代码规范和风格规则。
- PR 必须经过同行评审并获得批准。
- 如果变更修改了行为或增加了新功能，必须有相应的文档记录。
- 性能基准测试必须通过，确保无性能退化。

## 治理

本宪法是项目开发实践的指导文件。任何对本宪法的拟议修改都必须以拉取请求的形式提交，经团队审查和批准后方可合并。所有开发活动都必须与此处概述的原则保持一致。本宪法为QoraTrader项目的最高治理文件，所有开发实践、技术决策和代码实现必须符合本宪法原则。任何对宪法的修改需经过项目核心团队评审并记录变更理由。所有代码审查和质量检查必须验证对宪法原则的符合性。
