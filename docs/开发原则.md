# CBTrader 项目章程

## 核心原则

### I. 清晰与简洁
代码编写必须尽可能清晰、简洁且易于维护。避免过早优化和不必要的复杂性。坚守“你不会需要它”（YAGNI）原则。所有代码都应能让新加入项目的开发者轻松理解。

### II. 严格的测试驱动开发 (TDD)
**所有代码都必须严格遵循测试驱动开发模式。** 任何新功能或错误修复都严禁在没有对应失败测试的情况下进行开发。开发工作流必须强制执行“红-绿-重构”循环：
1. **红**: 为每一个微小的功能变更或修复，首先编写一个明确失败的自动化测试。
2. **绿**: 编写最精简的代码，仅为了让该测试通过。
3. **重构**: 在测试持续通过的保障下，优化代码结构，消除重复，提高可读性。

**此原则不可协商。**

### III. 工具一致性
项目将使用一套标准化的工具进行开发、构建、测试和部署。这确保了一致性，减少了配置偏差，并为所有团队成员简化了开发环境的搭建。任何新工具都必须经过批准并在项目的 README 文件中记录。

### IV. API 优先设计
所有服务和组件都应采用 API 优先的方法进行设计。在开始实施之前，定义并记录 API 契约。这确保了组件的接口定义良好，并能满足其消费者的需求。

### V. 语义化版本控制
项目严格遵守语义化版本控制 2.0.0。所有发布版本都必须采用 `主版本号.次版本号.修订号` 的格式。

### VI. 统一的用户体验
所有面向用户的组件必须遵守通用的设计体系和交互模式。跨应用的界面元素、术语和工作流程必须保持一致，以确保为用户提供可预测且直观的体验。

### VII. 卓越的系统性能
系统必须以响应迅速和高效为设计目标。必须评估新功能的性能影响。关键用户交互和API端点必须满足已定义的性能基准（例如，延迟、吞吐量）。

## 开发工作流

所有工作都应在从 `main` 分支创建的特性分支上进行。禁止直接向 `main` 分支提交代码。每个特性、错误修复或变更都必须创建一个拉取请求 (PR)。每个 PR 在合并前必须由至少一名其他开发者审查和批准。

## 质量门禁

在 PR 可以合并之前，必须通过以下质量门禁：
- 所有现有和新增的测试都必须通过。
- 代码必须遵守项目的代码规范和风格规则。
- PR 必须经过同行评审并获得批准。
- 如果变更修改了行为或增加了新功能，必须有相应的文档记录。

## 治理

本章程是项目开发实践的指导文件。任何对本章程的拟议修改都必须以拉取请求的形式提交，经团队审查和批准后方可合并。所有开发活动都必须与此处概述的原则保持一致。
